# The sabotage sentinel

Incident authority is outside every candidate repository. Candidate-controlled workflows cannot safely hold a dispatch or GitHub App credential: candidate code run earlier in the same job can persist, write `GITHUB_ENV`, or leave a background process. Therefore `templates/sentinel.yaml` is only a credential-free static diagnostic. It has no dispatch step, no observer secret, no delivery transport, no release authority, and no authoritative incident claim.

## Candidate diagnostic

The candidate workflow checks out candidate bytes without credentials or submodules and invokes independently pinned `tools/incident_probe.py`. The probe performs bounded no-follow reads, AST parsing, report-text inspection, and changed-workflow text inspection. It never imports candidate modules, runs candidate scripts, invokes a candidate `gate.py`, executes generators such as `recompute.py`, starts task code, runs hooks, or writes into the candidate tree. It recognizes only reviewed static affirmative predicates: inert instruments, explicit bypass syntax on the gate step of a changed workflow, and a SHIP disposition paired with one of those static findings. An instrument is inert when it returns only constants or coverage gaps and never raises, asserts, or calls anything but a gap helper. Bypass syntax counts only inside the step or job that invokes a gate tool, so `|| true` on a cache purge or `continue-on-error` on an unrelated job is housekeeping rather than evidence. A clean probe is not a broad integrity verdict.

`TRINITY_PROBE_REPO` and `TRINITY_PROBE_SHA` in a candidate repository are local workflow configuration, not proof of independent governance. Branch protection, CODEOWNERS, immutable pins, and external observation must be provisioned separately and verified by administrators. If those controls are absent, the candidate check remains a useful diagnostic but cannot authenticate or authoritatively record anything.

## Independently governed observer

Install `templates/sentinel-observer.yaml` only in a separately governed observer repository. Its supported producer contract is an independently deployed GitHub App webhook bridge controlled by governance. The bridge receives GitHub push and pull-request events and sends `repository_dispatch` type `sentinel-observe` to the observer repository with exactly three positive signed-64-bit integers: target `repository_id`, Actions `run_id`, and `run_attempt`. The bridge's GitHub numeric sender ID and the observer repository's immutable numeric ID must appear in owner-only incident configuration outside candidate storage.

The observer does not trust caller-asserted actor, repository name, ref, commit, finding, or timestamp metadata. It authorizes the actual `${{ github.actor_id }}` and `${{ github.repository_id }}` of the dispatch against external allowlists, then uses an observer GitHub App token to resolve the target repository by numeric ID, fetch the named Actions run attempt, require a supported `push` or `pull_request` event, bind the run's repository ID, actor ID and login, immutable head SHA, run start time, run ID, and attempt number, and verify the commit through the GitHub API. It checks out that exact commit as data with submodules disabled and credential persistence disabled, reruns the reviewed static probe, and constructs the incident only from API-authenticated context plus the probe result. It does not consume `workflow_run` artifacts or execute a candidate parent gate.

Pull-request observation requires that external GitHub App webhook bridge. GitHub intentionally withholds repository secrets from untrusted pull requests, so there is no safe candidate-workflow substitute. If the bridge, App installation, API access, allowlist, or observer runner is unavailable, complete PR incident collection is unavailable and release policy must fail closed rather than claim coverage.

The observer transactionally ingests an incident into external state and ends. The workflow contains no delivery job or schedule. Operators inspect durable state with the read-only `status` or `check` command; those commands make no network request and cannot clear a repeat alert.

## Trusted configuration and infrastructure

The owner-only JSON configuration uses schema `trinity.incident-store-config/v2` and names `state_dir` and `candidate_roots` as canonical `./` paths anchored to the trusted process working directory captured at CLI startup, plus non-empty `allowed_sender_ids`, non-empty `allowed_observer_repository_ids`, non-empty `allowed_target_repository_ids`, a repetition threshold, and time bounds. The config file and state directory must be owned by the observer account, grant no group or other permissions, remain outside candidate roots, and contain no symlink directory ancestor or escape. Absolute paths, home expansion, backslashes, traversal, and config-selected roots are refused. The deployed defaults are `./.incident-service/config.json`, `./.incident-service/state`, and `./candidate-data`, all beneath the governance root while state remains outside the candidate tree. Threshold cannot be below two or above one hundred; time windows, event age, future skew, document size, JSON depth and node count, identifiers, code count, and run-attempt integers all have explicit bounds.

```json
{"allowed_observer_repository_ids":["87654321"],"allowed_sender_ids":["12345678"],"allowed_target_repository_ids":["11223344"],"candidate_roots":["./candidate-data"],"max_age_seconds":86400,"max_future_skew_seconds":300,"schema":"trinity.incident-store-config/v2","state_dir":"./.incident-service/state","threshold":5,"window_seconds":2592000}
```

Provision an isolated `trinity-trusted-observer` self-hosted runner for API validation, static data inspection, and durable ingestion. Provision an observer GitHub App with read-only access to Actions metadata, repository metadata, commits, and candidate contents for explicitly approved repositories; a separate webhook/dispatch capability restricted to the observer repository; a full immutable SHA for observer source; a persistent owner-only volume that survives runner and host replacement; and operational monitoring for unavailable runners, failed App delivery, failed API validation, and unavailable state. A GitHub-hosted runner filesystem and workflow artifacts are not durable state. This repository does not fabricate any of that infrastructure.

## Incident identity, ordering, and status

An event identity is derived from immutable target repository ID, authenticated run ID, and run-attempt number. Exact redelivery is idempotent. Conflicting content under the same identity is refused while a digest-only equivocation diagnostic is committed. Run attempts are retained for forensic identity, but retries of one run ID do not count as distinct suspected-tampering attempts; threshold counting requires distinct authenticated run IDs. Related events share an affirmative finding code; a shared actor alone never relates two events, because one person tripping two different refusals is not a pattern. Ingestion evaluates both sides of the time window, so newest-first arrival still records exactly one repeat alert for the newest related event.

SQLite stores incidents, equivocation diagnostics, and immutable repeat-alert rows transactionally in the external state directory. Concurrent ingestion produces one alert per selected event. `status` emits bounded authenticated identifiers and digests suitable for human inspection and returns nonzero only when at least one threshold-crossing repeat alert exists; a lone incident or equivocation does not masquerade as a repeated alert. `check` additionally runs SQLite integrity and foreign-key checks. Neither command mutates or clears authoritative records, and no operator-facing reset command exists.

Existing `incidents.sqlite3` files migrate in place without losing incident or equivocation rows. A legacy mail queue table is renamed to inert `legacy_mail_outbox_v1`, retaining every column and unknown value, and each referentially valid legacy row seeds a repeat-alert record before the versioned database migration is marked complete. The active store never queries the archived table after migration. `migrate-config` accepts only the known v1 schema, writes an exact owner-only `.legacy-v1` backup that preserves unknown data, then atomically replaces the active file with the closed transport-free v2 fields; it never reads a credential environment variable. Unknown schema versions fail closed.

## Local diagnostic ledger

`tools/sentinel.py` remains diagnostic, never authoritative. It deduplicates repository/run/code records, counts all codes in one run as one repetition attempt, and uses a Unix `fcntl.flock` across the complete ledger read-modify-write. Every existing `.sentinel` component used for ledger, head, lock, clearance, or quarantine operations must be a real in-root directory or regular file; symbolic links, devices, FIFOs, directories where files belong, and out-of-root paths are refused. File opens use `O_NOFOLLOW` where available. Malformed heads are chain breaks, a present head with a missing ledger is rollback, and corrupt regular forensic bytes are moved into an in-root quarantine before replacement rather than unlinked. A clearance is a DSSE envelope at `.sentinel/clearances/<alert entry hash>.json.dsse` under payload type `application/vnd.trinity.sentinel-clearance+json`, verified against `.memory/allowed_signers` and authorized by the `sentinel_clearer` role in `.memory/roots.yaml` with the alerted actor's verified principal excluded. A legacy typed `<alert entry hash>.json` naming an approver clears nothing and is itself the refusal `SAB_SENTINEL_CLEARANCE_UNSIGNED`, and an attempt whose HEAD commit carries no signature this repository can verify is attributed to the claimed identity `unverified:<author>`, which names no principal a clearance may rest on.

```bash
python3 ./trinity/tools/sentinel.py verify ./
python3 ./trinity/tools/sentinel.py status ./
python3 ./trinity/tools/sentinel.py clear ./ --alert <entry-hash> --key ./.secrets/clearer-key --reason "reviewed the attempts"
python3 ./trusted-observer/tools/incident_store.py migrate-config --config ./.incident-service/config.json
python3 ./trusted-observer/tools/incident_store.py ingest --config ./.incident-service/config.json --event ./.trinity-runtime/incident.json --sender-id 12345678 --source-repository-id 87654321
python3 ./trusted-observer/tools/incident_store.py status --config ./.incident-service/config.json
python3 ./trusted-observer/tools/incident_store.py check --config ./.incident-service/config.json
```
