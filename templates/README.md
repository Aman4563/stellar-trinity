# Templates

`sentinel.yaml`, the six git hooks `pre-commit`, `pre-merge-commit`, `post-checkout`, `post-merge`, `post-rewrite`, and `pre-push`, and `gitattributes` are candidate gate templates. `release-gate.yaml` and `sentinel-observer.yaml` are different: governance installs them only in separate publisher and observer repositories, and candidate installation is forbidden.

## Nobody installs these by hand

`trinity/tools/gate.py install` runs inside every gate preflight, so any pasted ENGRAM, FORGE, or CRUCIBLE contract installs the parent's gates before it does phase work. In one idempotent pass it:

1. Copies only `sentinel.yaml` to `.github/workflows/`; the external publisher owns `release-gate.yaml`, and the external observer owns `sentinel-observer.yaml`.
2. Copies every hook of the roster to `.githooks/<name>`, marks each executable, and sets `git config core.hooksPath .githooks`.
3. Merges the four lines of `gitattributes` into the parent's `.gitattributes`, line by line the way CODEOWNERS is merged so a parent keeps its own attributes, then sets `merge.trinity-generated.name` to `Trinity generated report; keep ours and re-render` and `merge.trinity-generated.driver` to `true`.
4. Merges `/.github/ @EtharaOrion/research` and `/trinity @EtharaOrion/research` into `.github/CODEOWNERS` (override the team with `TRINITY_CODEOWNERS_TEAM`).
5. Applies branch protection on `main`, through `gh api`, to the parent repository and to every repository behind a `deliverables` or `staging` submodule: required candidate qualification check `gate` with strict status, rules enforced for administrators, no force pushes, no deletions, linear history. Direct pushes to `main` are lawful and no pull request review is required: every runner pushes a reconciled tree straight to `main`, and the required check on the pushed commit is the admission. Final protected publishing remains an externally deployed governance control and is not claimed by this template.

A second run changes nothing. A protection the CLI cannot apply, because `gh` is absent, unauthenticated, or refused, is a receipt with `applied: false` and the reason, the command exits 2, and `check_gates_installed` refuses the parent with `GATE_PROTECTION_MISSING` until the read-back confirms the rule. Commit `.github/`, `.githooks/`, and `.gitattributes` alone, before any report or harness change, so the gate surfaces never share a commit with their subject.

```sh
python3 ./trinity/tools/gate.py install ./ [--repo owner/name] [--dry-run]
```

## release-gate.yaml

### Collaborative disposition signing

New team promotions default to closed `trinity.release-disposition/v3` when the external governance root defines both `gate_producer` and `gate_approver`; governance supplies membership and thresholds, and promotion never self-enrolls the invoker. V3 retains every v2 project, repository, full snapshot, bundle set, candidate commit, verifier, issue, expiry, instrument, and SHIP field, but replaces scalar `producer` and `approver` with exactly `producer_role: gate_producer` and `approver_role: gate_approver`. Its purpose-specific domains are `application/vnd.trinity.release-disposition.v3.forge+json` and `application/vnd.trinity.release-disposition.v3.crucible+json`. Verification derives identities from authenticated signatures, satisfies the producer threshold first, excludes every qualifying producer signer from the approver set, then satisfies the approver threshold; repeated signatures and aliases resolving to one authenticated principal count once. Revoked, expired, outsider-only, under-threshold, or self-approval sets fail closed. Existing valid v2 records retain their exact payload domains and scalar checks, and `gate.py promote --approver NAME` intentionally keeps the named v2 form.

For a small company, configure disjoint 1-of-N producer and 1-of-N approver groups; use 2-of-N where governance requires two distinct people. Each person keeps an individual software key and runs `sign-partial` over identical persisted bytes, so teammate B can take over production and teammate C can approve without A's private key. Inspect progress without any key using `python3 -I ./trusted-signer/tools/gate.py signing-status --root ./candidate-data --instrument FORGE|CRUCIBLE --trust-dir ./release-trust --envelope ./.trinity-runtime/PERSON.dsse [--envelope ./.trinity-runtime/OTHER.dsse] [--complete-envelope ./candidate-data/HARNESS/disposition.json.dsse]`; output contains authenticated principals, each role's threshold and missing count, and completion, never identity assertions from arguments or secrets. Assemble arbitrary partials with repeatable `--envelope`; when `--output` already exists, `cosign-assemble` validates and retains its signatures, adds new matching partials, and replaces it atomically without reading a private key. Legacy `--producer-envelope` and `--approver-envelope` flags remain accepted.

Governance invokes the external workflow with immutable candidate and optional export repository names, numeric GitHub repository ids, and full commit SHAs. The protected `release-governance` environment owns `TRINITY_EXPECTED_PROJECT_ID`, `TRINITY_EXPECTED_PARENT_REPOSITORY_ID`, optional `TRINITY_EXPECTED_SAMPLES_REPOSITORY_ID`, verifier repository and SHA, and trust repository and SHA. The trusted runner requires each supplied repository id to equal its governance-owned expected id and the id resolved through the GitHub API, requires the external policy project id, parent repository id, and verifier SHA to equal the governance pins, checks out candidate and export only as data, and runs only the independently pinned verifier. No candidate workflow, script, import, evaluator, or bundle executable runs, and checkout credentials are not persisted.

The template intentionally has only `workflow_dispatch`; push and pull-request triggers would return control to candidate repository configuration. `GOVERNANCE_READ_TOKEN`, expected repository identities, verifier pins, and trust pins belong to the external publisher. Actual protected publishing deployment and secret administration remain external operational work.

The external trust checkout is passed as `TRINITY_RELEASE_TRUST_DIR` and contains exactly `roots.yaml`, `allowed_signers`, `trusted-root-version`, and `policy.json`. The root version must equal, not merely exceed, the pinned integer. Closed `trinity.release-policy/v3` binds immutable `project_id`, `repository_id`, full `verifier_sha`, positive `disposition_max_age_seconds`, and oracle policy. Oracle policy includes pinned Harbor/image/harness identities, positive reward and finite score bounds, run count and age, non-empty `required_controls`, non-empty `positive_control_ids`, and `non_applicable_controls`. Required controls cannot omit any of the six core controls: `build_assets_harness`, `oracle_noop_known_wrong_adversary_integrity`, `alternate_correct_mutant_grading_instruction_scope`, `judge_completeness_repeatability`, `trial_reward_accounting`, or `execution_fidelity`. Only trusted policy may mark the judge control non-applicable; execution fidelity is always applicable and may be a positive control.

Each signed `trinity.oracle-run/v4` receipt includes exactly one outcome for every required control. Every outcome binds its control id, pass or trusted non-applicable status, evidence digest, task uuid, trusted verifier SHA, and a common manifest closure digest. Missing, failed, skipped, deferred, waived, duplicate, or extra controls refuse release. There is no legacy acceptance route for older receipt or release-policy schemas: every parent must re-issue its policy and obtain fresh receipts. The authorized execution service signer is trusted to observe actual execution; local fixtures and this verifier do not prove that execution independently, and absent external quality-executor receipts therefore fail closed.

FORGE and CRUCIBLE retain separate v2 payload types, `application/vnd.trinity.release-disposition.forge+json` and `application/vnd.trinity.release-disposition.crucible+json`, for exact backwards-compatible named records, and use the v3 payload types documented above for group records. Every record binds instrument, project and repository identity, complete release snapshot digest, bundle-set digest, immutable candidate commit, trusted verifier SHA, issue and expiry instants. V2 requires its authenticated scalar producer and authorized named approver; v3 requires its two distinct-principal role quorums. Copying one instrument or schema envelope into another domain fails.

`gate.py promote` converts a substantive `SHIP_ELIGIBLE` qualification record to the final record only while the qualification record still binds HEAD through its gate-sealing commit. Omit `--approver` for the default group-v3 record; use explicit `--approver NAME` only for named-v2 compatibility. The signer administrator invokes from a governance root containing read-only `./trusted-signer` and `./release-trust`, immutable data at `./candidate-data`, role-separated software private keys below `./.secrets`, and mode-`0700` staging at `./.trinity-runtime`; none may fall back to candidate-local code or trust. Individual principals each run `python3 -I ./trusted-signer/tools/gate.py sign-partial --root ./candidate-data --instrument FORGE|CRUCIBLE --trust-dir ./release-trust --key ./.secrets/ROLE-key --output ./.trinity-runtime/ROLE.dsse` on their own machine. Every external CLI and config path must begin `./`; absolute host paths, home expansion, backslashes, traversal segments, and symlink escapes are refused, while internal resolved `Path` values exist only for containment and security checks and are never emitted. Before private-key access, the trusted signer copies only regular candidate object and index bytes into a signer-owned disposable bare repository with no hardlinks, validates candidate config as inert text, rejects executable config, includes, top-level `.git` indirection, commondir, and object alternates, and runs an absolute trusted Git binary with a minimal environment, no system or global config, no lazy fetch, no candidate hooks, and no configured filters, external diffs, text converters, or fsmonitor. That pinned Git executable is an internal operational dependency, not an authored project path. Candidate config, refs, hooks, and Git attributes are never installed into the trusted metadata repository. The same safe metadata boundary protects static `release.py` status, submodule, ancestry, and changed-path checks. Nobody copies a private key into the candidate, shares one between roles, or collects role keys locally. Transfer only partial envelopes and inspect v3 progress with `signing-status`. The same trusted checkout runs `python3 -I ./trusted-signer/tools/gate.py cosign-assemble --root ./candidate-data --instrument FORGE|CRUCIBLE --envelope ./.trinity-runtime/signer-1.dsse --envelope ./.trinity-runtime/signer-2.dsse --output ./candidate-data/HARNESS/disposition.json.dsse`, adding repeatable `--envelope` arguments until both role thresholds are complete; it receives no private key and stores none. FORGE and CRUCIBLE may seal in separate commits, but the complete range after the bound candidate snapshot may change only their four final disposition record and envelope paths.

Software keys are mandatory. Hardware security keys, physical tokens, FIDO discovery, HSMs, `sk-ssh-ed25519@openssh.com`, `sk-ecdsa-sha2-nistp256@openssh.com`, and both security-key certificate forms are forbidden, not optional alternatives. Create the recommended software Ed25519 key in a role-specific service account with `mkdir -p ./.secrets && chmod 700 ./.secrets`, then run `ssh-keygen -t ed25519 -C 'levi-attestor@partner' -f ./.secrets/levi_attestor` and enter a passphrase when prompted. Protect the private file with mode `0600` and enroll only the public `./.secrets/levi_attestor.pub` bytes in external governance trust. A CI-managed secret, OS keychain export to a short-lived mode-`0600` file below `./.secrets`, or encrypted key file unlocked only in the signer job are acceptable software choices. Use a different software key and account for the approver, mount candidate and trust snapshots read-only, and never put either private key in the candidate checkout, candidate environment, logs, artifacts, or network payloads.

Canonical bundle identity remains per UUID bundle, while the release snapshot separately binds every samples byte, including shared README, reward schema, and `.github`, excluding only top-level `.git`. Top-level population is closed to UUID bundle directories, `.github`, `README.md`, and `reward-schema.json`; arbitrary objects fail. Bounded no-follow reads, copied Git object and index bytes, and metadata consistency checks reduce ordinary races, but they do not turn a mutable candidate worktree into a transaction: governance must present an immutable read-only filesystem snapshot for the entire signing or verification interval. That requirement never permits running Git against candidate-local configuration.

The canonical identity intentionally replaces the legacy pipeline hash that followed symlinks as link text and ignored executable bits. Existing queue seals created with that legacy algorithm fail closed as moved bytes and must be re-sealed under the shared versioned identity; they are never silently migrated or treated as equivalent.

Versioned migration may preserve read-only signed v2 and v3 disposition bytes but never reserializes them or grants authority. An unknown disposition schema, changed signed bytes, or missing current validation holds for explicit governance action; migration never creates a key, enrolls a principal, changes `gate_producer` or `gate_approver` membership or thresholds, or converts historical signatures into approval of changed bytes.

## sentinel.yaml

Installs a candidate-side diagnostic `gate` status check with no secret, dispatch, delivery, or release authority. It checks out candidate bytes without credentials or submodules, checks out an independently pinned static probe from `TRINITY_PROBE_REPO` at full `TRINITY_PROBE_SHA`, verifies that pin, and runs only `probe/tools/incident_probe.py` over candidate data and the changed-path list. Authoritative incident observation and durable retention remain in the separately governed observer workflow, while release authority remains in the publisher workflow described by `SENTINEL.md`.

## The hook roster and gate.py

`gate.py` runs the qualification check list: every substantive semantic, integrity, pipeline, Harbor, sabotage, and sentinel check, but not final release authorization and not its own current receipt prerequisite. This breaks the circular dependency without bypassing semantic checks. The external publisher runs the complete final release policy and refuses absent signed SHIP evidence.

### The six hooks

Every hook opens with `set -u`, resolves the parent root through `git rev-parse --show-toplevel` and `cd`s into it, refuses when `trinity/tools/pipeline.py` is absent, and creates `.sentinel` before it writes a log there. No hook issues `git add`, `git commit`, `git push`, `git stash`, or `git checkout`: a hook writes working-tree bytes at most and names the paths for a human to stage.

| Hook | Trigger | Command | Exit semantics and log |
|---|---|---|---|
| `pre-commit` | every commit | `python3 trinity/tools/pipeline.py render-reports ./ --check --staged > .sentinel/pre-commit-reports.txt 2>&1` | exit 0 allows the commit; a nonzero exit refuses it, repeats every `wrote ` line of the log on stderr, and tells the reader to review the rendered bytes and stage them. Log `.sentinel/pre-commit-reports.txt` |
| `pre-merge-commit` | a merge commit | `python3 trinity/tools/pipeline.py render-reports ./ --check --staged > .sentinel/pre-merge-reports.txt 2>&1` | identical semantics, so a merge cannot land a tracker that disagrees with the merged tree. Log `.sentinel/pre-merge-reports.txt` |
| `post-checkout` | after a checkout | `python3 trinity/tools/pipeline.py render-reports ./ --check > .sentinel/post-checkout-reports.txt 2>&1` | a file checkout, which git signals by passing `0` as the third argument, exits 0 at once; otherwise a failed check prints `trinity gate: TRACKING.md is stale for this checkout` on stderr with the command that fixes it. Always exits 0. Log `.sentinel/post-checkout-reports.txt` |
| `post-merge` | after a merge updates the worktree | `python3 trinity/tools/pipeline.py render-reports ./ > .sentinel/post-merge-reports.txt 2>&1 \|\| true` | advisory refresh that writes the rendered bytes, prints every `rendered ` line, and always exits 0. Log `.sentinel/post-merge-reports.txt` |
| `post-rewrite` | after a rebase or an amend | `python3 trinity/tools/pipeline.py render-reports ./ > .sentinel/post-rewrite-reports.txt 2>&1 \|\| true` | the same advisory refresh; its leading `cat > /dev/null` drains the rewritten-ref list so the hook never takes SIGPIPE. Always exits 0. Log `.sentinel/post-rewrite-reports.txt` |
| `pre-push` | every push | `python3 trinity/tools/pipeline.py reconcile ./ --check`, then `python3 trinity/tools/pipeline.py verify ./ --accepted "$remote_sha"` for every ref the push updates, then `python3 trinity/tools/gate.py ./ --instrument CRUCIBLE --moment report --check --json` | gate exit 0 allows the push, exit 2 allows it and names the HOLD ceiling, exit 3 refuses it on the BLOCK ceiling, and any other exit refuses it naming the finding and the preflight that refreshes a drifted hook. Logs `.sentinel/pre-push-reconcile.txt`, `.sentinel/pre-push-streams.txt`, `.sentinel/pre-push.json`, and `.sentinel/pre-push.err` |

`render-reports` is report-only: it renders `TRACKING.md` and the root reports from the tree and never moves a bundle. Hooks run `reconcile ./ --check` and `render-reports` in check or render mode, never a bare `reconcile`, which renames bundle directories. Check mode exits 3 on `REPORT_NOT_RENDERED`, `REPORT_NOT_STAGED`, `REPORT_INPUTS_UNSTAGED`, or `REPORT_STAGED_UNAVAILABLE`; with `--staged`, it also writes expected report bytes for the human to review and stage.

### Merge verification

Before the gate check the hook runs `pipeline.py reconcile ./ --check`, refusing a push whose tree differs from its own reconciliation, and `pipeline.py verify ./ --accepted <remote sha>` for every ref the push updates, refusing a queue stream the remote already holds that was rewritten rather than extended. Inside that same ref loop it refuses a local sha that is neither the zero sha nor `git rev-parse HEAD`, because a reconciliation of HEAD says nothing about an older commit, so `git push origin HEAD~1:main` is named rather than passed. All three are pure functions of the tree, so continuous integration on `main` reruns them on the pushed commit and reaches the same answer. Direct pushes to `main` are lawful; the hook is the admission and the rerun names a bypass.

### The generated-report merge driver

`gitattributes` carries exactly four lines, `TRACKING.md merge=trinity-generated`, `DIRECTIVE.md merge=trinity-generated`, `EDICT.md merge=trinity-generated`, and `VERDICT.md merge=trinity-generated`. Those files are rendered from the tree rather than hand-authored, so a textual three-way merge of two renderings produces a file that is a function of nothing. The installed driver is `merge.trinity-generated.driver` set to `true`, whose binary leaves `%A` in place and exits 0, which keeps the local rendering and lets the next hook re-render the merged tree; `merge.trinity-generated.name` carries the reason, `Trinity generated report; keep ours and re-render`. The driver is never `union`.

### What check_gates_installed refuses

`check_gates_installed` byte-compares every installed hook against its template and emits `GATE_HOOK_MISSING` for one that is absent or drifted, emits `GATE_ATTRIBUTES_MISSING` when `.gitattributes` lacks any of the four required lines, and emits `GATE_MERGE_DRIVER_MISSING` when `merge.trinity-generated.driver` is unset or is not `true`, or when `merge.trinity-generated.name` has drifted. All three are errors rather than advisories, because the merge policy is load-bearing. Each names `trinity/tools/gate.py install` as the remedy, and install rewrites a drifted hook, merges a missing attribute line, and sets the config keys again.

### No release waivers

Any `.audit/release-waiver.json` is rejected. Operational acceptance is not SHIP and cannot clear a FORGE disposition, CRUCIBLE disposition, oracle execution, reward, identity, or export refusal.
