# Hostile-operator hardening rollout

## Purpose

This document explains the release and alert controls added after the 2026-09-07 delivery failure, how a client obtains independently governed release evidence, which older evidence is invalid, and which protections remain blocked. It is a rollout guide and limitation register, not proof that any external service has been deployed.

## Trust boundaries

### Current collaborative disposition interface

New team promotions use closed `trinity.release-disposition/v3` by default when the external governance root already defines `gate_producer` and `gate_approver`; governance owns both membership and thresholds, and no command auto-enrolls its caller. V3 retains the v2 instrument, disposition, project, repository, complete snapshot, bundle set, immutable candidate commit, verifier, issue, and expiry bindings, replaces scalar `producer` and `approver` with exactly `producer_role: gate_producer` and `approver_role: gate_approver`, and signs purpose-specific domains `application/vnd.trinity.release-disposition.v3.forge+json` and `application/vnd.trinity.release-disposition.v3.crucible+json`. The final verifier authenticates every DSSE signature, deduplicates by returned principal rather than keyid hints, satisfies the producer threshold first, excludes all qualifying producer signers from the approver set, and then satisfies the approver threshold with revocation and expiry evaluated at verification time. One software private key repeated or roster-aliased cannot meet a distinct-principal quorum, one principal cannot count for both roles, and outsider-only or under-threshold sets fail closed. Existing valid `trinity.release-disposition/v2` records retain their exact scalar verification and payload domains, and `gate.py promote --approver NAME` remains the explicit named-v2 interface; no broader migration is implemented in this lane.

Any authorized teammate can sign the same persisted bytes with an individual software key, so B can resume production and C can approve while A is absent and no private key is transferred. `gate.py signing-status --root ./candidate-data --instrument FORGE|CRUCIBLE --trust-dir ./release-trust` accepts repeatable `--envelope ./...` plus optional `--complete-envelope ./...`, authenticates identity from signatures, and reports role thresholds, qualifying principals, missing counts, and completion without reading keys or printing secrets. `gate.py cosign-assemble` accepts arbitrary repeatable `--envelope ./...`, retains the old `--producer-envelope` and `--approver-envelope` flags, validates exact payload and domain equality, incorporates a valid existing output for cross-session resumption, rejects duplicate signatures, and atomically replaces the output without key access. A small company can use disjoint 1-of-N producer and 1-of-N approver groups; governance may independently raise either role to 2-of-N.

The candidate operator, candidate checkout, parent checkout, local root reports, local sentinel state, and trust files committed inside the candidate tree are untrusted. FORGE emits candidates. CRUCIBLE audits candidate bytes but cannot authorize publication by prose, waiver, skipped control, or coverage gap. ENGRAM remembers only verified measured evidence and cannot promote an authored or missing result. The candidate gate may produce substantive `SHIP_ELIGIBLE` qualification but never final release. The release authority is a separately governed publisher repository that exclusively owns `release-gate.yaml` and fixes the verifier, trust, repository identities, and policy before it observes the candidate.

Every hardening interface uses one path doctrine. The trusted orchestrator fixes the governance or invoking project root as the process working directory at CLI startup. Every path string in configuration, CLI arguments, generated signing commands, workflow staging, persisted JSON, and diagnostics is canonical POSIX form beginning `./`; `./` itself denotes the root. Absolute paths, home expansion, backslashes, `..` segments, redundant segments, and symlink escapes are refused, and candidate bytes or config-file contents never select or change the root. Implementations may resolve an accepted path to an absolute `Path` solely for containment, no-follow reading, ownership, executable pinning, and other security checks, but never serialize or print that host path. External release trust, software private keys, incident state, and runtime staging remain outside the resolved candidate tree while staying inside the governed root, for example `./release-trust`, `./.secrets/approver-key`, `./.incident-service/state`, and `./.trinity-runtime/incident.json` beside `./candidate-data`. Fixed system executable paths in `tools/safe_git.py`, the administrator-pinned SSH executable API, and operating-system sentinels such as `/dev/null` are internal operational necessities rather than authored project paths and do not relax this rule.

The publisher must present the candidate repository, optional export repository, independently governed verifier, and release-trust repository as immutable snapshots for the full verification interval. Governance owns expected numeric candidate and export repository identities and pins verifier and trust by full commit SHA. Closed `trinity.release-policy/v3` binds immutable `project_id`, `repository_id`, trusted verifier SHA, disposition age, and oracle policy. The verifier computes canonical per-bundle and bundle-set identities plus the complete release snapshot digest over every admitted export byte, including shared README, reward schema, and `.github`, excluding only top-level `.git`, and binds the immutable candidate commit. The release-trust snapshot contains exactly `roots.yaml`, `allowed_signers`, `trusted-root-version`, and `policy.json`; the root version must equal the policy pin. A deployed publisher never accepts repository identity, trust directory, root version, signer roster, verifier repository, or verifier SHA selected by the candidate operator.

FORGE and CRUCIBLE each produce a closed disposition record under a distinct instrument payload type. New promotion defaults to group `trinity.release-disposition/v3` with `application/vnd.trinity.release-disposition.v3.forge+json` or `application/vnd.trinity.release-disposition.v3.crucible+json`, while existing valid signed v2 bytes and explicit `gate.py promote --approver NAME` retain the exact named-v2 payload types. Every record binds instrument, project and repository identity, complete release snapshot digest, bundle-set digest, immutable candidate commit, trusted verifier SHA, and issue and expiry instants. V3 binds the external `gate_producer` and `gate_approver` roles and requires their positive thresholds with producer principals excluded from approval; v2 binds an authenticated scalar producer and authorized named approver. A signer administrator independently obtains and pins a read-only trusted signer checkout and release-trust checkout outside the candidate. Individual principals independently run that trusted `gate.py sign-partial` under Python isolated mode on their own machines, pass `./candidate-data` only as `--root` data, retain separate external software private keys, and transfer only partial envelopes; candidate `./candidate-data/trinity` code and candidate-local trust are never executed or loaded with a key available. Before key access, `tools/safe_git.py` validates candidate Git control files as bounded inert text, rejects executable config, includes, top-level `.git` indirection, commondir, and object alternates, copies only regular object and index bytes without hardlinks into a signer-owned disposable bare repository, and uses an absolute trusted Git executable under a minimal environment with system, global, and candidate config disabled, lazy fetching disabled, and candidate hooks, filters, external diffs, text converters, fsmonitor, and attributes unable to supply a command. Static release verification uses the same repository for dirty-tree, submodule, ancestry, tree, and changed-path queries. The trusted signer validates the unsigned candidate record completely before key access, while `gate.py cosign-assemble` checks schema-specific payload type and exact payload equality and combines partials without receiving a private key. Copying one instrument or schema envelope into another domain fails. Root-report SHIP text remains a consistency check and never authorizes release.

The authorized external execution service is trusted to observe benchmark execution and quality controls. Each exported bundle requires a canonical DSSE receipt with schema `trinity.oracle-run/v4`, exact bundle identity, policy-pinned Harbor, image, and harness identities, a valid time window, positive finite `full_reward`, equal reward, bounded score, uniquely identified stability runs, and exactly one coverage outcome for every policy-required control. The controls manifest must include `build_assets_harness`, `oracle_noop_known_wrong_adversary_integrity`, `alternate_correct_mutant_grading_instruction_scope`, `judge_completeness_repeatability`, `trial_reward_accounting`, and `execution_fidelity`. Every outcome binds control id, pass or trusted non-applicable status, evidence digest, task uuid, trusted verifier SHA, and a common manifest closure digest. Missing, failed, skipped, deferred, waived, duplicate, or extra outcomes fail closed, and only trusted policy may mark the judge control non-applicable. Execution fidelity is always applicable and may be required as a positive control. `tools/release.py` verifies those signed observations and does not execute Harbor, reconstruct the benchmark run, or prove execution or universal semantic correctness. The external quality-controls runner that must produce genuine v4 receipts remains absent.

Candidate `sentinel.yaml` is a local static diagnostic with no secrets, dispatch, delivery, or release authority. It checks out candidate bytes without credentials or submodules and runs only an immutable reviewed `incident_probe.py`; it never runs candidate scripts. The authoritative observer lives in a separately governed repository and accepts `repository_dispatch` only from a deployed allowlisted GitHub App webhook bridge. It authorizes immutable sender and observer-source repository identities from governance config, resolves target repository, run attempt, run id, actor, ref, and commit through the GitHub API, authorizes the resolved target repository id, checks out that commit as immutable data, and reruns the reviewed probe read-only. `tools/incident_store.py` stores closed incidents, equivocations, and threshold-crossing repeat alerts transactionally in an external SQLite volume. Its bounded `status` output returns nonzero only for a meaningful repeat alert, and no command clears authoritative state or sends a message. The GitHub App bridge, App token, sender and source and target allowlists, durable storage, isolated observer runner, repository rulesets, and operational monitoring are deployment obligations rather than repository facts.

## Obtaining independent release evidence

For the current v3 path, enroll individual software identities in externally owned `gate_producer`, `gate_approver`, and `execution_operator` roles before promotion. Keep producer and approver membership disjoint where practical, choose 1-of-N or 2-of-N thresholds deliberately, omit `--approver` to mint v3, collect only partial envelopes, inspect them with `signing-status`, and assemble with repeatable `--envelope`. Supplying `--approver NAME` intentionally stays on v2 for safe existing integrations.

1. Establish separate administrative ownership for the publisher, verifier repository, release-trust repository, quality-controls execution service, observer repository, and GitHub App bridge. Prevent candidate maintainers from changing protected variables, secrets, required checks, allowlists, or pinned commits.
2. Enroll distinct producer, gate approver, and execution operator principals in the external root and matching allowed-signers policy. Set a positive trusted root version and complete the dual-threshold rotation ceremony for every later root change.
3. Install `release-gate.yaml` only in the governance publisher repository. Set expected candidate and export numeric repository ids, pin verifier and release trust by full commit SHA, and present candidate and export commits as immutable snapshots. Candidate `gate.py install` is qualification-only and cannot deploy or prove this publisher.
4. Publish closed `trinity.release-policy/v3` with project and repository identity, verifier SHA, disposition age, oracle identities and bounds, and a required-controls manifest containing all six core controls. Run the external quality-controls service against each exact bundle under that policy and produce one `trinity.oracle-run/v4` receipt per bundle only after every required control has exactly one acceptable outcome under the common closure digest.
5. Promote substantive FORGE and CRUCIBLE qualifications into separate closed group `trinity.release-disposition/v3` records binding the same complete release snapshot, bundle set, candidate commit, verifier, project, and repository by omitting `--approver`; use explicit `--approver NAME` only for named-v2 compatibility. From the governance root, use `TRUSTED_SIGNER_CODE_DIR=./trusted-signer`, `TRUSTED_RELEASE_TRUST_DIR=./release-trust`, `CANDIDATE_ROOT=./candidate-data`, a role-specific key such as `./.secrets/approver-key`, and mode-`0700` staging at `./.trinity-runtime`. Have individual principals independently run `python3 -I ./trusted-signer/tools/gate.py sign-partial "--root=$CANDIDATE_ROOT" --instrument FORGE|CRUCIBLE --trust-dir "$TRUSTED_RELEASE_TRUST_DIR" --key ./.secrets/ROLE-key --output ./.trinity-runtime/ROLE.dsse`, using separate keys that are never placed in the candidate or collected together, exchange only partial envelopes, inspect threshold progress with `gate.py signing-status`, and run the trusted `gate.py cosign-assemble` with repeatable `--envelope ./.trinity-runtime/ROLE.dsse` only after all exact domain-separated payloads match.
6. Run the pinned verifier with governance-fixed trust against immutable candidate and export snapshots. Preserve the policy, verifier and trust pins, repository identities, snapshot and bundle-set digests, candidate commit, co-signed dispositions, v4 receipts, and verifier result for client review.
7. Deploy the allowlisted GitHub App webhook bridge and separately governed observer. Configure independent sender, observer-source, and target repository-id authorization, API-resolve every target run, let the observer rerun `incident_probe.py` read-only before admitting an incident, retain the incident database on owner-only durable storage, and monitor ingestion and storage availability without claiming a synthetic watchdog.

## Minimal software-key setup

Standard software Ed25519 keys satisfy the signing design, and software keys are the only permitted class. Physical security keys, FIDO discovery, HSMs, `sk-ssh-ed25519@openssh.com`, `sk-ecdsa-sha2-nistp256@openssh.com`, and both security-key certificate forms are forbidden. Create one Unix or CI service account per producer or approver role, create `./.secrets` with mode `0700`, run `ssh-keygen -t ed25519 -C 'levi-attestor@partner' -f ./.secrets/levi_attestor`, enter a passphrase when prompted, set the private file to mode `0600`, and enroll only the `./.secrets/levi_attestor.pub` bytes in the independently governed signer policy. Small teams may store the private key in a CI-managed secret, an OS keychain that materializes a short-lived mode-`0600` file below `./.secrets`, or an encrypted file unlocked only inside the isolated signer job. Use distinct accounts and software keys for producer and approver, prevent either account from reading the other's key, mount the trusted signer code, external trust, and candidate snapshot read-only, and delete any short-lived plaintext key file after signing. Never hardcode a real private key, copy it into candidate storage, expose it to candidate processes or environment, attach it to an artifact, or send it over the network; only the resulting partial DSSE envelope leaves the signer. The backend reads the bounded public header embedded in an OpenSSH private key and refuses a hardware or unsupported algorithm before invoking `ssh-keygen`; verification independently parses the SSHSIG public-key and signature fields plus each `allowed_signers` public blob, so a textual or armored-header spoof cannot bypass the policy.

The candidate and export must remain immutable for the entire safe-metadata copy, worktree comparison, signature validation, and release decision. Per-file no-follow reads and before-and-after metadata checks detect ordinary replacement races, and Git object plus index bytes are copied before trusted Git parses them, but a hostile mutable filesystem can still present mutually inconsistent files across separate reads. A read-only snapshot is therefore mandatory. It is an additional consistency property, not permission to execute candidate `.git/config`, includes, hooks, attributes commands, filters, diff drivers, fsmonitor, alternates, lazy fetchers, or inherited `GIT_*` settings.

## Migration and invalidation

Existing valid v2 disposition records and signatures remain accepted exactly; they are not weakened, rewritten, or silently migrated. New promotion defaults to v3 after governance enrolls `gate_producer` and `gate_approver` and sets positive thresholds. The versioned migration journal may retain read-only signed v2 and v3 bytes, but unknown disposition formats hold and migration never grants authority, creates keys, changes roles or thresholds, or rewrites an envelope.

Only release-policy v3 and oracle-run v4 are accepted. There is no legacy acceptance route for older policy or receipt schemas, including the former five-control versions; every parent must re-issue its release policy and obtain fresh receipts. Every `trinity.release-disposition/v1` or legacy unversioned disposition also remains invalid for current release. Regenerate evidence from immutable current candidate and export bytes under policy v3, rerun all six required core controls through the still-separate quality-controls service, issue v4 receipts with the complete controls manifest and closure digest, and create new default group disposition v3 records binding the full release snapshot digest and candidate commit. Individual role principals must create new instrument-domain partial signatures and assemble new envelopes; old signatures do not migrate, while explicit `--approver NAME` remains available only for a required named-v2 disposition integration, never for an older release policy or oracle receipt. Any path, file byte, executable bit, shared export file, candidate commit, verifier pin, trust pin, policy field, controls evidence, or disposition payload change invalidates the affected evidence.

A candidate-local `.memory/roots.yaml`, `.memory/allowed_signers`, or `.memory/trusted-root-version` never substitutes for the external release-trust snapshot. Existing local roots may continue to serve contract-local attestation checks, but they authorize no external publication. Migrate publisher configuration to protected full-SHA verifier and trust pins before accepting a release result.

Any `.audit/release-waiver.json` now causes `RELEASE_WAIVER_INVALID`. Preserve historical waivers as historical records outside the active candidate release path if governance requires retention, but remove them from the candidate snapshot before a release request. Record any decision to proceed operationally against the existing HOLD or BLOCK disposition. Do not relabel it SHIP.

Local sentinel ledgers, candidate workflow actors, and candidate-authored event payloads do not migrate into authoritative notification state. Provision the external observer and database, establish the independent GitHub App bridge sender identity and governance-owned observer-source and target allowlists, and admit only API-resolved run identity after the observer reruns the probe. Do not import candidate-authored actor identities or infer intent from prior local records.

## Residual authority

An administrator who controls the publisher, verifier pins, trust repository, execution signer, observer, rulesets, credentials, and external state remains outside this repository's threat boundary. A client requiring defense against that actor needs independently witnessed transparency records and client-side re-execution. The current hardening raises the last line of defense against a candidate operator; it does not convert one organization into its own independent witness.
