# Project-structure migrations

Trinity migration is versioned compatibility software, not a waiver. It upgrades only the closed legacy matrix below, preserves exact originals in immutable content-addressed backups, and leaves unknown, unsafe, signed, or unprovable state at `HOLD` with a path-specific action. Backward compatibility means that supported old bytes can advance without discarding task identifiers or pending work. It does not mean that unknown future metadata, stale signatures, changed evidence, empty versions, or unsafe paths are accepted.

## Entry points

An authoring preflight, `python3 ./trinity/tools/gate.py ./ --instrument DOMAIN --moment preflight`, runs the compatibility planner before installation or phase work and applies safe known transformations. `--check`, report-moment gates, promotion, signing, signing-status, cosign assembly, and final release verification never apply migration. Operators can inspect the same plan with `python3 ./trinity/tools/migrate.py ./ --json` and apply it explicitly with `python3 ./trinity/tools/migrate.py ./ --apply --json`. Every CLI path is a canonical lexical `./` path captured beneath the process working directory; absolute paths, backslashes, `..`, redundant segments, and symbolic-link traversal are refused.

The historical queue digest is reproduced exactly from the source introduced in commit `07aca95`: sorted relative file paths, a NUL-delimited `file` or `symlink` discriminator, decimal byte length, payload, and a trailing NUL. The migrator accepts that algorithm only to prove an existing seal against the bytes currently present. The current identity still refuses symbolic links and binds regular-file bytes plus executable bits. Historical records for bytes no longer present are retained as history rather than guessed into a new identity.

## Progress and revalidation

As of 2026-09-18, the five refused-schema rows above are revalidation paths, not transformations. The migrator detects each legacy policy at `./.seed/pilot-policy.json`, each legacy line at `./.seed/pilot-attempts.jsonl`, execution envelopes under `./.audit/attestations/execution/`, and oracle receipts under `./.audit/receipts/oracle/`, the receipt directory used by `release.py`. It decodes DSSE payloads only to inspect schema identifiers, never to authenticate or accept them. Every instance produces a path-specific `needs_revalidation` record carrying its source schema and the exact Limit action above; JSONL records also carry their line number. Neither inspection nor application rewrites any of those source bytes.

External release policy discovery uses the same selector as `release.py`: explicit `--trust-dir ./governance` takes precedence over `TRINITY_RELEASE_TRUST_DIR`. The selected directory must be inside the invoking governance root and outside the candidate tree. Migration reads only its `policy.json`, not keys, trust roots, or signer enrollment, and records the policy path relative to the invoking governance root with an `external governance` label. No configured directory means no external policy inspection, not proof that a current policy exists; release verification still requires external trust. Run from the governance root with the candidate named as `./candidate` when checking an external policy.

`--check --json` and the default `--json` inspection write nothing. `--apply --json` records the findings in `./.trinity/migrations/needs-revalidation.json` through the existing journal, whose report step has status `needs_revalidation`; unrelated supported transformations can still complete. The migration report remains `hold`, exits with status 2, and keeps the authoring preflight at `HOLD` while any refused instance remains, including on repeated checks. A completed write journal does not discharge a revalidation obligation. Re-issuance is human-governed fresh work through the current pilot, attestation, audit, and release validators, never a schema-string edit or reuse of an old signature. This matrix does not change feedback-chain `github_id` compatibility.

Migration never fabricates a verdict. A pending queue item keeps its uuid and producer run id and remains pending under the current digest. If a legacy digest had a verdict, the verdict and any DSSE envelope remain byte-for-byte unchanged, no old signature is reserialized, and `./.trinity/migrations/needs-revalidation.json` names the uuid and required audit plus re-signing action. A migrated Harbor manifest likewise requires a new digest-bound Harbor validation receipt and new signatures for any affected release evidence. The authoring gate stays at `HOLD` while the matching current receipt or verdict is absent. Existing valid individual `trinity.release-disposition/v2` payloads remain valid only for the bytes they already bind and are never rewritten into group form. New group disposition v3 remains the default promotion path under externally enrolled `gate_producer` and `gate_approver` roles; governance may choose 1-of-N or 2-of-N thresholds, partial envelopes can accumulate across sessions, and `signing-status` reports authenticated principals and missing role members without reading a private key. Enrollment, threshold changes, root rotation, key creation, and trust membership remain human governance outside migration.

## Journal and backups

The progress folder `./.trinity/migrations/` is unsigned operational state and grants no authority. `state.json` has the closed top-level fields `version`, `steps`, `before_sha256`, `after_sha256`, `backups`, and `status`. Version is the integer `2`; status is one of `planned`, `applying`, `complete`, or `hold`. Every step has exactly `id`, `path`, `before_sha256`, `after_sha256`, `backup`, `before_mode`, `after_mode`, `needs_revalidation`, and `status`, with status drawn from `pending`, `applied`, or `needs_revalidation`. Every recorded path starts with `./` and is project-root relative. Plan hashes bind each ordered step's id, path, before or after hash, exact backup reference, original and target regular-file modes, and revalidation bit. Unknown versions, extra fields, inconsistent plan hashes, duplicate ids, impossible status combinations, unsafe modes, authority or signing paths, or a target matching neither recorded hash and mode hold closed.

Before replacing an existing file, the migrator creates `./.trinity/migrations/backups/<before_sha256>` with `O_EXCL`, mode `0400`, exact original bytes, and no clobber. An existing backup is reused only if its digest and mode match. Replacement preserves the original safe regular-file mode, including its executable bit; a new file starts at `0600`, and set-id, sticky, group-writable, or world-writable source or journal modes hold rather than escalate permissions. Journal and target replacement use an fsynced temporary file in the same directory followed by atomic rename and directory fsync; backup, lock, directory creation, and lock removal also sync the containing directory. A mode-`0600` exclusive lock prevents concurrent application. On every incomplete journal retry, the migrator first reconstructs the complete original virtual snapshot from verified immutable backups plus untouched before-state files, re-derives the full supported operation sequence, and requires exact equality of every bound step field before it uses only the newly derived paths and bytes. A target at its proved before hash and mode remains pending, while a target at its proved after hash and mode is finalized even if interruption occurred after atomic replacement but before the completed-step journal write. If an ordinary write or postcondition failure occurs, writes from that attempt roll back in reverse order with original bytes and modes, newly created targets are removed, the journal enters `hold`, and a later run resumes the same closed plan. Process interruption may leave `applying` state, but never authorizes a fresh plan that omits already replaced operations. A tampered backup, self-consistent but re-bound journal, unknown incomplete schema, migrated target, mode, or stale lock is an actionable hold, never a reason to overwrite.

## Authority boundary

A human creates `staging/` beside `samples/` and `delivery/`, as a plain directory with `mkdir staging` or as a submodule with `git submodule add <url> staging`, at the operator's choice. The parent gate holds on `missing shared directory "staging/"` until the directory exists in either form. No matrix row creates it, and the v2 project manifest never names it.

The five roster roots are submodules of the parent, `trinity/`, `.memory/`, `samples/`, `delivery/`, and `harness/`, each against its own distinct remote with `branch = main` and `update = merge`, and every bundle lives complete at `samples/<uuid>/` or `delivery/<uuid>/` inside its own submodule checkout. A parent holding a lane root as a plain directory creates the remote, registers the submodule with `branch = main` and `update = merge`, moves the resident bundle directories into the submodule checkout, commits them there, and records the gitlink in the parent, before the next gate. No matrix row performs that change, and the parent gate holds at `PARENT_LAYOUT_PLAIN_DIRECTORY` until it is done.

A parent still holding `deliverables/` moves each `deliverables/<uuid>/trajectories/` into `<lane>/<uuid>/trajectories/` for whichever lane root already holds that uuid, commits inside that lane submodule, records the moved gitlink in the parent, then deregisters `deliverables` from `.gitmodules` and removes the directory. No matrix row performs that change either, and the parent gate holds at `PARENT_LAYOUT_RETIRED_ROOT` until the root is gone. Because bundle identity excludes the bundle's own `trajectories/` subtree, moving that subtree changes no bundle identity; it does change the release snapshot digest, which follows the ordinary `needs_revalidation` re-sign path this document already defines.

Multi-runner layout is additive. A parent that ran under one clone keeps `.podium/queue.jsonl`, `.seed/lanes.yaml`, `.audit/verdicts/<uuid>.json`, `.audit/queue.claims/<uuid>.json`, `.sentinel/attempts.jsonl`, and the harness-root `disposition.json` and `gate-receipts/` as the legacy stream, registry, and records, all still read. New runs write beside them: `.podium/queue/<run_id>.jsonl`, `.seed/lanes/<uuid>.yaml`, `.audit/verdicts/<uuid>/<digest>.json`, `.audit/queue.claims/<uuid>/<run_id>.json`, `.sentinel/streams/<run_id>/`, and `<harness>/runs/<run_id>/`. The first `pipeline.py reconcile` renders `samples/README.md`, `delivery/README.md`, and every root report that run reports determine, and routes any resident bundle past thirty into `delivery/`; a legacy resident with no seal record is fixed where it stands and counted first. ENGRAM's first `epochs.py publish` snapshots the authoritative memory files into epoch 1. No matrix row performs any of this; the tools do on the next run.

The migrator is software-only and never creates or enrolls a key, opens a private key, changes a trust root or role threshold, edits an approval file, writes an allowed-signers policy, mutates a signed envelope, promotes a disposition, or writes outside the candidate project root. It does not move arbitrary old directories, perform generic text replacement, infer unknown schemas, update external Harbor installations, run Harbor's validator, or claim a current Harbor migration complete without its new receipt. Manual migration remains necessary for layouts outside the table, but manual work does not grandfather evidence: changed candidate bytes require the ordinary validation, audit, approval, and signing paths again.
